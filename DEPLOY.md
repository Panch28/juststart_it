# Deployment guide

This app is a **full-stack** application: an Express API with a SQLite database
plus a React single-page frontend. That shapes where it can be hosted.

---

## Read this first: why not Vercel alone

Vercel is an excellent host for the **frontend**, but it cannot run this
**backend** as-is. Vercel serverless functions:

- have a **read-only** filesystem except `/tmp`,
- have an **ephemeral** `/tmp` that is wiped between invocations, and
- run as **many independent instances**, each with its own memory and disk.

This API stores its SQLite database (`server/data/rih.sqlite`) and uploaded
documents (`server/uploads/`) on disk. On Vercel that means: data resets on
every cold start, uploads disappear, and two requests can see two different
databases.

Running it on Vercel therefore needs one of:

1. **A separate backend host with a disk** (recommended, see Option B), or
2. **A migration to hosted Postgres/libSQL** (Turso, Neon, Supabase). This is a
   substantial rewrite: every query in the 14 route modules uses the synchronous
   `node:sqlite` API (`db.prepare(...).get/.all/.run`), whereas hosted clients
   are asynchronous. It is not a config change.

Option A below avoids the problem entirely by deploying the whole thing to one
service that is allowed to keep files on disk.

---

## Option A — Render (recommended: one URL, one service)

A `render.yaml` blueprint is included at the repository root.

1. Push this repository to GitHub (see *Publishing to GitHub* below).
2. In Render: **New → Blueprint**, choose the repository.
   Render reads `render.yaml` and creates the service.
3. Click **Deploy**. First build takes a few minutes.
4. Your app is live at `https://<service-name>.onrender.com`.

What the blueprint does:

| Setting | Value |
| --- | --- |
| Build | `npm install && npm run build` |
| Start | `npm run seed && npm start` |
| Health check | `/api/health` |
| `NODE_VERSION` | `22.14.0` (required — `node:sqlite` needs ≥ 22.5) |
| `SESSION_SECRET` | generated by Render |

**Free-plan behaviour:** the disk is ephemeral, so on each restart the start
command re-creates and re-seeds the database. Visitors always get complete
sample data; changes made through the UI do not survive restarts. Free
instances also sleep after ~15 minutes idle and take ~50 seconds to wake.

**To keep data long-term:** attach a persistent disk and uncomment the
`DATA_DIR` / `UPLOAD_DIR` entries in `render.yaml` (a paid instance type is
required for disks).

## Option B — Vercel frontend + API elsewhere

Use this if you specifically want the site on a `*.vercel.app` domain.

1. Deploy the backend with Option A first and note its URL, e.g.
   `https://research-innovation-hub.onrender.com`.
2. Edit `web/vercel.json` and replace `REPLACE-WITH-YOUR-API-HOST` with that
   host (**https://**, no trailing slash).
3. In Vercel: **Add New → Project**, import the repository, and set
   **Root Directory** to `web`.
4. Framework preset **Vite**; build `npm install && npm run build`; output `dist`.
5. Deploy.

The `rewrites` rule proxies `/api/*` from the Vercel domain to the API, so the
frontend keeps using same-origin `/api` paths and the session cookie keeps
working. No frontend code changes are needed.

## Publishing to GitHub

The repository is already initialised and committed locally. From the project
root:

```bash
# Create an empty repository on github.com first, then:
git remote add origin https://github.com/<your-username>/<repo-name>.git
git branch -M main
git push -u origin main
```

Or, with the GitHub CLI:

```bash
gh auth login
gh repo create research-innovation-hub --public --source=. --push
```

`.gitignore` already excludes `node_modules/`, `web/dist/`, `server/data/`,
`server/uploads/` and `.env`, so no secrets or generated files are published.

## Quick share without any account (temporary)

For a fast "take a look" link, expose your running local server through a
Cloudflare quick tunnel:

```bash
npm run build && npm start          # terminal 1 — serves the app on :4000
cloudflared tunnel --url http://localhost:4000   # terminal 2
```

`cloudflared` prints a `https://<random-words>.trycloudflare.com` URL. It works
from any browser and needs no account, but:

- it lives only while the tunnel **and** your local server keep running,
- it changes every time you restart the tunnel,
- it is a public URL — anyone with it can sign in with the demo accounts.

Download `cloudflared` from
<https://github.com/cloudflare/cloudflared/releases>.

## Environment variables (all hosts)

| Variable | Default | Notes |
| --- | --- | --- |
| `PORT` | `4000` | Render/Vercel set this automatically |
| `SESSION_SECRET` | dev fallback | **Must** be set on any public deployment |
| `NODE_VERSION` | — | Must be ≥ `22.5.0` for `node:sqlite` |
| `DATA_DIR` | `server/data` | Put on a persistent disk to keep the database |
| `UPLOAD_DIR` | `server/uploads` | Put on a persistent disk to keep uploads |
| `CLIENT_ORIGIN` | `http://localhost:5173` | Only needed if serving the frontend from a different origin |

## Before sharing publicly

This is a **demonstration system**, not production software:

- authentication is a seeded demo login, **not** production-secure;
- all people, projects, IPR records and funding data are fictional;
- the IPR module tracks administrative workflow only — it makes no legal
  patentability determination;
- the funding catalogue is sample data and never submits an external application.

Anyone with the URL can sign in. Do not put real or confidential data into it.
