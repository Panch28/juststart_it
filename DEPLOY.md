# Deployment guide

This app has two parts: a React single-page frontend and an Express API backed by
SQLite. Both can run in one process (a normal Node host) or be split (static
frontend + serverless API).

- **Vercel** — works, in demo mode. See below for what that means.
- **Render / Railway / any VPS** — works with a real on-disk database.
- **GitHub** — the repository is already published.

---

## Option A — Vercel (single project, one URL)

This is the quickest way to get a public link. A root `vercel.json` and a
serverless entry point are included:

```
vercel.json                  build: web app + API bundle
api/[...path].js             catch-all function → bundled Express app
api/_bundle.cjs              generated by `npm run build:api`
scripts/build-api.mjs        esbuild bundling step
server/src/lambda.ts         serverless entry (schema + seed, then the app)
```

### Deploy

```bash
npx vercel login          # browser login, once
npx vercel --prod         # from the repository root
```

Or import the repository at <https://vercel.com/new> — no CLI needed. Vercel
runs the build command from `vercel.json` automatically.

### How the database works there

Vercel functions have **no persistent filesystem**. Only `/tmp` is writable, and
each instance gets its own copy. So on Vercel the app switches to a different
mode automatically (when `VERCEL=1` is present):

| | Vercel | Normal host |
| --- | --- | --- |
| Database | in-memory SQLite | `server/data/rih.sqlite` |
| Seeding | once per instance, on first request | `npm run seed` |
| Uploads | `/tmp/uploads` (per instance) | `server/uploads/` |

Every instance boots a complete, self-consistent copy of the demo dataset, so
**reads always work** and the dashboard, projects, IPR records, approval
workflow, startups, funding, analytics and role permissions all behave
correctly.

**Limitation you should know about:** writes (creating a project, approving a
request, uploading a document) are stored only in the memory of the instance
that handled them. They look successful, and are visible while that instance
stays warm, but they are **not durable** and other instances will not see them.
That is fine for a demo and unacceptable for real records.

If you need durable data on a serverless platform, the database has to move to
a hosted Postgres/libSQL (Neon, Turso, Supabase). That is a real rewrite: all 14
route modules use the synchronous `node:sqlite` API (`db.prepare(...).get()`),
while hosted clients are asynchronous. Use Option B instead if you need
persistence today.

## Option B — Render (persistent database)

A `render.yaml` blueprint is included at the repository root.

1. Push the repository to GitHub.
2. In Render: **New → Blueprint**, choose the repository.
3. Click **Deploy**. Your app is live at `https://<service-name>.onrender.com`.

| Setting | Value |
| --- | --- |
| Build | `npm install && npm run build` |
| Start | `npm run seed && npm start` |
| Health check | `/api/health` |
| `NODE_VERSION` | `24.14.0` (`node:sqlite` needs ≥ 22.5; 22.13+ has it unflagged) |
| `SESSION_SECRET` | generated by Render |

On the **free** plan the disk is ephemeral, so the start command re-seeds on
every restart — visitors always see complete sample data, but writes do not
survive restarts. Attach a persistent disk and uncomment `DATA_DIR` /
`UPLOAD_DIR` in `render.yaml` to keep data across deploys (paid instance type
required).

## Rebuilding the serverless bundle

`api/_bundle.cjs` is a build artefact that is committed so a deploy cannot fail
because of build ordering. Regenerate it after changing anything under
`server/src/`:

```bash
npm run build:api
```

The bundle embeds `server/src/db/schema.sql` at build time, so the function
never depends on a file sitting next to it on disk.

## Environment variables

| Variable | Default | Notes |
| --- | --- | --- |
| `PORT` | `4000` | Hosts set this automatically |
| `SESSION_SECRET` | dev fallback | **Set this** on any public deployment |
| `CLIENT_ORIGIN` | `http://localhost:5173` | Only for a split frontend/API setup |
| `DATA_DIR` | `server/data` | Put on a persistent disk to keep the database |
| `UPLOAD_DIR` | `server/uploads` | Put on a persistent disk to keep uploads |
| `DB_PATH` | `<DATA_DIR>/rih.sqlite` | Set to `:memory:` to force demo mode |

Vercel sets `VERCEL=1` on its own; that is what enables in-memory mode.

## Quick share without any account (temporary)

To show the running local copy to someone without deploying:

```bash
npm run build          # terminal 1
npm start
cloudflared tunnel --url http://localhost:4000   # terminal 2
```

`cloudflared` prints a `https://<random-words>.trycloudflare.com` URL. It needs
no account, but it dies when the tunnel or your machine stops, and the URL
changes each time.

Download `cloudflared` from
<https://github.com/cloudflare/cloudflared/releases>.

## Before sharing publicly

This is a **demonstration system**, not production software:

- authentication is a seeded demo login, **not** production-secure;
- all people, projects, IPR records and funding data are fictional;
- the IPR module tracks administrative workflow only — it makes no legal
  patentability determination;
- the funding catalogue is sample data and never submits an external
  application;
- anyone with the URL can sign in as any demo role.

Do not put real or confidential data into it.
